Security

Built to sit on the internet.

A browser terminal for your servers is a powerful thing to put online. Here is what protects it, and what it cannot protect you from.

Start with the honest part.

Anyone who gets all the way past the login gets, on every host their account reaches, the access of the user its agent runs as, much like holding an SSH key for that user. Roles limit which hosts an account reaches and whether it gets a shell there, not what a shell can do. So the work goes into making “all the way past the login” hard: below is what a stolen password alone does not get you.

That is why the defaults are strict: HTTPS on a real domain, passkeys, and an agent that runs as a dedicated, unprivileged webterm user unless you decide otherwise.

A stolen password is not enough.

  • Accounts with 2FA

    Signing in also asks for the authenticator code, or is done with a passkey. A new passkey cannot be added without that second factor, so the password cannot be turned into a key of its own.

  • Hosts marked “Require 2FA”

    Every session, file action, command or update there needs a fresh passkey, authenticator code or SSO re-authentication; the account password alone is refused. Automation tokens are refused outright.

  • The window stays short

    After the second factor, the host stays open for 5 idle minutes and at most 60 minutes in all; then the terminal locks, shared viewers included, until you present a factor again.

  • What it cannot cover

    An account without any second factor, and hosts without the flag, are protected by the password alone; the Security card on the dashboard points out both. A device that is already signed in and inside its window is, for that window, you.

Getting in

  • Passkeys

    WebAuthn sign-in, with TOTP and recovery codes as alternatives.

  • Step-up per host

    Flag a host and everything there asks for a fresh second factor, never the password alone.

  • Single sign-on

    OIDC (Authentik bundled or your own) and SCIM provisioning; group-to-role mapping.

  • Lockout and alerts

    Failed sign-ins are throttled; new sign-ins and security changes are emailed.

After the login

  • Roles and scopes

    Owner, Admin, Operator, Viewer or your own roles; per host or folder; time-bound grants; crown-jewel hosts.

  • Command guardrail

    Admin rules that block a command, or ask for confirmation, before it runs, including in split views and Run on hosts.

  • Shares that cannot outgrow you

    A share or replay link never gives more than its creator still has, and dies when that access ends.

  • Audit log

    Who did what, from which IP. Tokens and secrets are kept out of it.

  • Security card

    The dashboard tells you what needs attention: a missing passkey, an open share, an old agent.

  • Scoped automation tokens

    Read or run only, expiring, capped by a role and a host scope, refused on 2FA hosts.

On your hosts

  • Nothing to expose

    The agent dials out. No port opens on the server, and the gateway stores no login for it.

  • One token per machine

    Bound to that host and individually revocable. Reinstalling an agent issues a new one.

  • A client certificate per agent

    From 3.7.0, each agent also proves itself with a certificate from your installation's own authority, checked during the TLS handshake. A client without one never reaches the gateway, and a copied token alone opens nothing.

  • Signed updates

    An agent only runs an update signed with your own key.

  • SSH host keys pinned

    A changed key raises an alarm instead of connecting.

New in 3.8

Encryption at rest, with a key you keep apart.

Until 3.7, the key that encrypts every stored credential (agent tokens, SSH passwords and keys, TOTP secrets, SMTP and cloud logins) sat in the same data volume as the credentials. From 3.8 it is locked with a master key kept outside that volume, so a copy of the volume or of a backup no longer gives them away.

  • A master key outside the data

    New installations get a key file outside the data volume, mounted read-only. Keep a copy off the machine: without it, the installation and its backups cannot be opened. A missing or wrong key stops the gateway before it touches anything; it never falls back to the old key.

  • Backups that never hold the key

    Every backup and snapshot the gateway writes is an encrypted container that only the master key opens, and the key is never inside it. The host backup script works the same way.

  • Host backups of any size

    The host backup streams the volume in small authenticated chunks, so a few gigabytes of recordings are no obstacle, and restores read it the same way. Both check the free space first and always leave a reserve for the gateway: at least 1 GiB or 5% of the disk, whichever is larger.

  • Encrypted session recordings

    Opt-in. Each recording gets its own key. Existing recordings are converted in the background, and the plaintext is deleted only after the encrypted copy is verified. An upgrade never turns this on for you.

  • Compressed before they are encrypted

    Encrypted data does not compress, so recordings are compressed first: on disk and in backups they stay close to the size of a gzipped plaintext, typically several times smaller. Recordings encrypted without it are recompacted in the background and replay exactly as before. On by default; WEBTERM_TX_COMPRESS=0 turns it off.

  • Erasing a recording is final

    An Owner erase destroys the recording’s key and writes the erasure to a journal that is copied to your SFTP or FTPS destination and read back. Restoring an older backup does not bring the recording back.

  • Quarantine instead of guessing

    When a restore cannot prove which erasures happened after the backup, the restored recordings are held back. They are released once the destination proves the history; until then an Owner can open one at a time, with a fresh second factor, and it is audited.

  • Visible in System health

    Whether the volume is protected, reduced or still legacy, how the recordings’ encryption and compression are going, and which older backups still hold the old key in clear, so you can delete them.

  • A one-way move from 3.7

    Upgrading changes nothing until you add a key. The next start checks that the old key really opens the database, then migrates once. Download a backup first: after the migration there is no way back to 3.7 on the same volume, and the deploy, rollback and upgrade scripts refuse to start an older image on it.

What it does not cover. The database file itself is not encrypted yet: host names, accounts and the audit log stay readable inside the volume. Encryption at rest protects a stolen disk, a copied volume or a backup. It does not protect a server that is running and compromised, because the running gateway holds the key. And because compressed sizes depend on the content, someone who can both type into a session and repeatedly watch the stored size of its recording could learn something about what was printed next to it; turn compression off if that matters to you.

Running it

  • Encrypted backups

    Daily, encrypted, and optionally off-host: Google Drive, Dropbox, SFTP or FTPS. From 3.8, with a master key configured, a backup opens only with that key and never contains it: keep a copy of the key off the machine, or the backups cannot be restored.

  • Pinned releases

    The upgrade script takes a version tag, not latest, and pins it to an immutable image digest before it switches.

  • Release checks

    The publish pipeline requires unit, browser and accessibility tests, a secret scan and a Python dependency audit. The image and npm scans run weekly, separately.

  • Reporting a vulnerability

    Privately, through GitHub. See the security policy.
